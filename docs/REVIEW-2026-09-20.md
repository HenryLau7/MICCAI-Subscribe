审查日期：2026-09-20。基线：`3de0632`。范围：前端路由、搜索、收藏与关注、日程与日历、导入导出、缓存/PWA、Python 数据流水线、生成数据、依赖、GitHub Actions、部署配置和本次 About 改动。

## 发现的问题

### 1. P1：卫星活动 ID 冲突，打开、收藏和导出的活动发生替换

位置：[`scripts/parse_satellite.py:171`](../scripts/parse_satellite.py#L171)，消费端 [`web/src/data/decode.ts:85`](../web/src/data/decode.ts#L85)。

ID 仅由日期、房间、起始时间段构成，但同一时间段可拆出多个活动。当前已发布数据中存在两组冲突：

| ID | 第一条活动 | 覆盖它的活动 |
| --- | --- | --- |
| `sat:2026-09-27:rome:2` | Mama-Synth | UUSIVC2026 |
| `sat:2026-10-01:madrid-1:2` | SASHIMI | SynthOCT |

`new Map(...)` 保留最后一条。点击 Mama-Synth 会打开 UUSIVC2026，收藏与日历导出也使用错误活动；SASHIMI 同理。111 条活动只有 109 个唯一 ID。现有数据校验器未检查卫星活动 ID 唯一性，带着该错误的数据仍通过校验。

建议：使用包含活动身份的唯一 ID，并在数据构建关卡拒绝重复 ID。处理旧收藏时不能把原本有歧义的 ID 自动猜成其中一个活动。

### 2. P2：机构归并把不同大学合并

位置：[`scripts/common.py:100`](../scripts/common.py#L100)。

`canonical_affiliation` 选取首个包含 School/College 等词的段落，再去掉前缀，可能丢弃大学名称。当前 `biomedical-engineering` 下有 8 篇论文，来自上海交大、上海科技大学、中山大学、清华、复旦；`computer-science` 下有 7 篇论文，来自 5 所不同大学。

复现：`School of Biomedical Engineering, Shanghai Jiao Tong University` 与 `School of Biomedical Engineering, Tsinghua University` 均返回 `biomedical-engineering`。关注机构因此会加入其他大学论文，也可能遗漏同一大学以其他名称归并的论文。

建议：优先保留完整大学身份；无法确定归属时保留完整机构信息，避免以通用院系名合并。

### 3. P2：多个标签页之间会丢失收藏

位置：[`web/src/store/StoreProvider.tsx:37`](../web/src/store/StoreProvider.tsx#L37)。

状态仅在挂载时读取，每次变更均用当前标签页的完整快照覆盖 localStorage，没有处理其他标签页的 `storage` 事件。

复现：空日程打开 A/B 两个标签页；A 收藏 `M-PM-001`，随后 B 收藏 `M-PM-002`。最终持久化状态仅剩第二项，A 刷新后第一项消失。用两个独立 provider 和一次 storage 事件复现。

建议：同步其他标签页的存储更新，并确保用户操作不会覆盖已经写入的新状态。

### 4. P2：首页搜索自动跳转时丢失输入焦点

位置：[`web/src/routes/SearchResults.tsx:43`](../web/src/routes/SearchResults.tsx#L43)，触发端 [`web/src/ui/SearchBox.tsx:43`](../web/src/ui/SearchBox.tsx#L43)。

首页输入后停顿 300 ms 会跳到 `/search`，原有输入框卸载，新搜索框没有接续焦点。复现中 `document.activeElement` 变为 body，用户继续打字无法更新查询。

建议：保留输入框实例，或仅在从首页搜索跳转时恢复焦点和光标位置。

### 5. P2：后台更新可覆盖唯一可用的离线数据

位置：[`web/src/data/load.ts:34`](../web/src/data/load.ts#L34)。

后台更新只判断 HTTP 成功就替换缓存，没有先解析或校验版本。若部署回退返回 200 HTML，或新数据与当前客户端 schema 不兼容，原有可用缓存被替换；下次离线打开时，加载器删除坏缓存后尝试联网，最终整个应用不可用。

复现：有效缓存 → 后台返回 200 HTML → 模拟离线 → 再次加载失败且缓存已删除。独立测试已复现。首次网络加载分支也在解码前写入缓存。

建议：完整解码成功后再替换缓存；失败时保留最后一份可用数据。

### 6. P2：日历导出的 Oral/Spotlight 顺序错误

位置：[`web/src/calendar/build.ts:52`](../web/src/calendar/build.ts#L52)。

编号在每种报告类型内从 1 重新开始；导出只按 `orderInSession` 排序，会交错排列两种报告。收藏 O1A 全部报告，描述中出现 `Oral 1, Spotlight 1, Oral 2, Spotlight 2, …`，而原顺序为 Oral 在前、Spotlight 在后。共 9 个混合 session 受影响。

建议：复用已经用于页面展示的 `bySlot` 比较器。

### 7. P2：联系人邮件链接被当成活动官网

位置：[`scripts/parse_satellite.py:57`](../scripts/parse_satellite.py#L57)。

列表解析取整行第一个 `<a>`。iMIMIC 标题没有官网链接，解析器便选中了联系人栏的 `/cdn-cgi/l/email-protection#…`。当前数据已含此值，点击活动官网会访问应用自身域名下的错误路径，ICS 也包含错误 URL。

建议：只从活动名称/缩写单元格提取官网链接，并在外部 URL 边界限制为有效 HTTP(S) 地址；没有官网时留空。

续做时补的两处边界（第 7 项的消费端，原审查只堵住了解析端）：

- **构建关卡校验 URL**：`validate.py` 现在对每条卫星活动的 url 复用同一个 `external_url`，非绝对 http(s) 直接让构建失败，而不是只靠解析器一道防线。
- **前端解码时过滤 URL**：[`web/src/data/decode.ts`](../web/src/data/decode.ts) 新增 `externalUrl()`，bundle 里不合法的链接解码为空串。渲染成外链 `<a href>` 和写进 ICS `URL:`（RFC 5545 不转义该字段）的值因此不会是相对路径或其他协议；未来 bundle 出问题时退化为“没有官网”，而不是错误链接。测试见 `web/test/decode.test.ts`。

失效的旧收藏不做猜测：ID 变化后旧收藏落到已有的 `unresolvedBookmarks()` 通道，在 `/schedule` 以横幅报出丢失数量，不会被静默映射到另一个活动，也不会被静默删除。

仍然存在、但属于取舍而非缺陷的两点：

- 一条机构串里写了两所大学（如 `ShanghaiTech University, Fudan University`）时取第一所；当前数据有 7 个这样的 key。
- 卫星活动 ID 只在冲突时带缩写后缀。好处是既有收藏不失效；代价是某个时段将来新增活动导致冲突时，该活动的 ID 会变一次（会被上面的横幅如实报出）。
